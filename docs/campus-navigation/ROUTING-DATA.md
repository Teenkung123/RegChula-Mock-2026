# Chula pedestrian routing data

## Integration contract

`navigation-data.json` is dependency-free static data: `{nodes,edges,buildings,metadata}`. All node/way IDs are **strings**. Nodes have `id,x,y,lon,lat` and schema-version-2 `elevationM`; metres x east / y north relative to EPSG:32647 (665434,1519346). glTF position is `[x, base height + elevationM, -y]`. Elevation is schematic, not surveyed.

Edges use `a,b,lengthM,wayId,highway,layer,bridge,tunnel,covered,sharedRoad,crossing,oneway,hasSteps,wheelchair`. Original path segments remain consecutive OSM node pairs. Revision 4 adds four reviewed original tunnel-approach segments and visibility segments contained entirely within three explicitly mapped pedestrian areas. Generated segments carry provenance; area segments have `pedestrianArea=true`. Do not re-snap or connect geometrically intersecting lines. `oneway` is **pedestrian-specific**: `yes` permits a→b, `-1` permits b→a; otherwise bidirectional. Motorvehicle oneway is ignored. Grade tags are retained; mixed-grade interior crossings receive distinct graph IDs, with original identities retained as provenance. Mapped two-grade structure/stair endpoints may remain transitions; ambiguous three-grade junctions are isolated. Rendering elevation is not surveyed and must not imply an indoor floor.

Building records use `code,aliases,name,nameTh,footprintId,x,y,accessNodeId,accessLabel,accessConfidence,accessOffsetM,source,osmSource,verifiedRooms,codeConfidence,roomParsing,accessibility`. Building x/y is the footprint centroid for highlighting only. **Route to accessNodeId, never draw a centroid connector through a building.** Access nodes are actual mapped points close to a footprint, not verified doors. MHMK endpoint happens to lie on the footprint boundary; TAB endpoint is ~0.9m from its footprint. No entrance/interior/gate availability is certified.

Official code/room mappings for MHMK and TAB are verified against https://www.bbtech.sc.chula.ac.th/building/ (checked 2026-10-18). MHMK M01 is floor M, TAB220 floor2. Other MHMK/TAB rooms listed in `verifiedRooms` come from the same official table. The original thirty-building index uses exact OSM `ref` matches against the app's course-building directory for other codes, with lower confidence. The 2026-10-19 extension below adds eighteen campus footprints and coalesces alternate codes. No guessed acronyms. Added access points are existing exterior graph nodes within30m of the footprint; original MHMK/TAB special checks allow60m but both <1m. Unmatched buildings remain unmapped.

### Timetable walking allowance

Navigation assumes a class may finish up to ten minutes early: departure is `max(class start, scheduled end - 10)` and available walking time is `next start - departure`. Scheduled times and the raw scheduled gap remain unchanged. A negative scheduled gap always remains an overlap warning, even when the estimate leaves positive walking time. The allowance is a planning estimate and does not change calendar, registration, or conflict rules.

Room parser should prioritize `verifiedRooms`. TAB permits the user's first-digit floor convention as an estimate bounded by four floors. MHMK official 19 stories vs OSM20 is a conflict; its real 201/301 convention also contradicts blindly taking two digits for every tall building. Thus unlisted MHMK and lower-confidence buildings should fall back to building arrival unless another trusted convention exists. A parsed floor is a label, not a 3D room coordinate or indoor route.

## Safety and limits

This is an outdoor **planning preview**, not surveyed navigation. Permission, opening hours, gates and closures are not live. Route may use stairs and shared low-speed roads, and is not wheelchair-verified. Preserve those route metadata flags; routine stairs/shared-road notices are omitted from the navigation summary. Always show OSM attribution and copyright link.

Conservative exclusions: foot=no/private/use_sidepath; any access value except yes/permissive/designated (including permit/destination/private/customers/delivery) unless foot explicitly yes/permissive/designated; motorroad, motorways/trunks/major traffic centreline classes, busways, construction, indoor corridors, unreviewed area polygons, unhandled conditional access. Low-speed service/residential/unclassified centreline ways are allowed only absent separate/no-sidewalk tags. Restricted, locked or conditionally accessible nodes are rejected. Node foot=use_sidepath is rejected. Ground segments entering building interiors are rejected (0.3m inward tolerance), except explicitly mapped tunnel=building_passage. Merely covered=yes does not exempt a wall crossing. Mapped wall/fence crossing segments are rejected unless a shared passable gate node exists or the exact source segment and exact fence are one of the four reviewed exceptions below. No arbitrary sidewalk, road-centreline, lawn, fence, or proximity shortcut is generated. Unresolved connections remain disconnected.

Estimate: ceil(outdoor path metres / 1.2 / 60). Excludes indoor movement, lifts, crossing waits and small unverified endpoint gaps. Example MHMK→TAB: **192.2m / ~3 minutes outdoors**, 16 segments, one stair segment, two shared-road segments. Never promise classroom-to-classroom 3 minutes.

## Reviewed pedestrian topology, 2026-10-20

The tunnel connection is corroborated by the university's [pedestrian-access report](https://sustainability.chula.ac.th/th/report/3373/), the [CU Tunnel Revival project](https://healthyspaceforum.org/portfolio/cu-tunnel-revival/), and the [university gate register](https://www.arts.chula.ac.th/~tran/downloads/cu_traffic_03.pdf). The exact mapped segments, fence IDs, source references, and review confidence are recorded in `pedestrian-review.json`. This evidence establishes a mapped connection, not current permission or opening hours. Historic source hours are retained only as provenance; affected routes display an access warning.

Only four source segments cross individually allowlisted fences: ways 836151470, 836151471, 836151472, and 1204350167 at the tunnel approaches. These exceptions do not disable other fence or building checks. The tunnel interior node 358215242 has no surface connection.

Only the explicitly pedestrian polygons 1425513646 (Sci Square), 1379251825, and 1100606098 (Atom Square) admit visibility edges. Their original closed rings are retained; every added segment must stay within its polygon, respect holes and concavities, and clear buildings, planting, water and barriers. Elevated or stair-incidence nodes cannot acquire plaza shortcuts. There is no general open-space mesh or inferred crossing of a major road.

The reviewed snapshot retains all 6,012 original edge identities and all 48 building records. It adds four approach edges and 137 plaza edges; isolating 23 mixed-grade junctions produces 5,515 nodes, 6,153 edges and 105 weakly connected components. MHMK→PINIT changes from 946.561 m to 441.049 m via the tunnel (about 7 outdoor walking minutes); MHMK→TAB remains 192.227 m. These are path-length estimates, not verified door-to-door trips.

The renderer uses ground 0, tunnel -3 and bridge +5 schematic metres per mapped layer, interpolated along mapped stairs. A bridge tag establishes a positive grade even without a layer tag. Ground-ended structure spans receive display-only shoulders so that a two-node bridge or underpass is not rendered flat; these points never change graph adjacency or the walking distance. The route ribbon and arrows follow the displayed grade, and underground legs remain visible through the ground when occlusion is enabled.

## Reproduce and validate

For the checked-in revision-4 overlay, install Shapely as a build/test dependency and run `python scripts/campus-routing/update_graph.py`, then `python scripts/campus-routing/test_graph.py`. The compiler consumes the bundled `pedestrian-source.json` and `pedestrian-review.json`, preserves original source edges and buildings, and deterministically replaces its own generated additions. Running it again must leave the JSON unchanged. No Python or geometry dependency is needed by the application at runtime.

`pedestrian-validation.json` records the fresh recovery audit dated 2026-10-21. `graph-validation.json` is explicitly historical: its original-edge-only claims and 5,469-node/6,012-edge counts describe the pre-overlay baseline, not the current graph. See `REVISION-4.md` for the current change scope and validation limits.

### Original research build (historical)

From original workspace, `python routing_data/build_graph.py`, then `python routing_data/test_graph.py`, then `python routing_data/audit_geometry.py`. Builder reads unchanged source OSM XML and expanded footprints from `chula_expanded_v2/source/`, merges duplicate IDs by highest version, and uses pyproj/shapely installed in `/tmp/chula_model_deps`. Audit visualization also uses matplotlib. No app runtime dependency is introduced.

Outputs: `navigation-data.json`, `source-way-tags.json`, `component-summary.json`, `example-route.json`, `validation-report.json`, `example-route-audit.png`. Geometry validation checks every edge against original node adjacency and building obstacles. Visually reviewed sample route stays outside footprints and follows mapped crossings/paths. Source OSM dataset is © OpenStreetMap contributors under ODbL; retain license metadata. Tests validate this snapshot, not real-world current walkability.

The original model/routing research source archives are separate from this feature overlay. The application consumes the bundled derived JSON directly. The scripts referenced above document the research build and are not required for application installation; refreshing the graph requires the original OSM inputs and another access/topology review.
